# Tritium v1.1 — Performance Overhaul + CUDA

## Context

Tritium v1.0 is a working C++17 header-only ternary compute library with 7 passing test suites covering packing, arithmetic, logic, thresholding, vectors, matrices, and convolution. However, an architecture audit revealed scalability bottlenecks that limit performance on workloads beyond ~100 elements: fragmented matrix storage, element-wise convolution, broken SIMD accumulation, and no GPU support. This overhaul fixes bugs, optimizes internals, and adds CUDA kernels while keeping the same public API.

## Scope

7 changes. Most are backward-compatible; breaking changes are noted explicitly.

**Implementation order** (dependency chain): 1 → 2 → 3+6 → 4 → 5 → 7

1. Fix SIMD + deduplicate popcount + fix GCC/Clang recursion bug
2. Contiguous TritMatrix with TritVectorView (depends on 1)
3. Word-level convolution (depends on 2 for sub-views)
4. Aligned allocator (independent)
5. API polish — operators, move semantics (independent)
6. Packed Volume3D (paired with 3)
7. CUDA kernels for batch operations (independent)

### Known Breaking Changes

These are intentional improvements where the old API was suboptimal:
- `TritMatrix::row()` returns `TritVectorView` instead of `TritVector&` — use `matrix.set(r, c, t)` for mutation
- `Volume3D::data` changes from `std::vector<Trit>` to packed `std::vector<TritWord64>` — use `set(d,h,w,t)` method
- `TritVector` internal storage type changes with aligned allocator — no impact on public API
- `dot()`, `hamming()` accept `TritVectorView` — implicit conversion from `TritVector` ensures existing call sites work

### Non-Goals (deferred to v2.0)

- Multi-stream CUDA (concurrent kernel execution)
- Batched matrix multiply on GPU
- Sparse trit representations (COO/CSR)
- Half-precision / mixed-precision support
- Streaming/out-of-core operations

## Change 1: Fix SIMD + Deduplicate popcount

### Problems
- `popcount64()` defined in both `trit.h` and `simd.h` (ODR risk)
- **Bug:** `trit.h` GCC/Clang path calls `popcount64(x)` recursively instead of `__builtin_popcountll(x)` — infinite recursion at runtime on non-MSVC compilers
- AVX2 `batch_dot` in `simd.h:88-99` has broken accumulator — computes bitwise results correctly but then does a pointless `_mm256_or_si256` before extracting to scalar, defeating the SIMD benefit
- `TritVector::dot()` has its own inline scalar implementation that duplicates `simd.h` logic — the SIMD path is never called from the most common entry point

### Solution
- Move `popcount64()` to `simd.h` as the single definition; fix the GCC/Clang path to call `__builtin_popcountll`
- `trit.h` includes a minimal inline version guarded by `#ifndef TRITIUM_SIMD_H`
- Rewrite `batch_dot` AVX2 path: use VPSHUFB nibble-lookup for horizontal popcount, accumulate in 256-bit register, extract only at the end
- **Wire `TritVector::dot()` to delegate to `simd::batch_dot()`** instead of duplicating the logic inline

### Files Modified
- `simd.h` — rewrite batch_dot AVX2 path, add `popcnt_epi64_avx2()` helper, fix popcount
- `trit.h` — guard popcount to avoid duplication, fix GCC/Clang recursion
- `trit_vector.h` — `dot()` calls `simd::batch_dot()` instead of inline implementation

### Expected Impact
~4x dot product speedup on AVX2 hardware (from ~2.5 to ~0.6 cycles/word)

## Change 2: Contiguous TritMatrix + TritVectorView

### Problem
`TritMatrix` stores `std::vector<TritVector> rows_` — each row is an independent heap allocation. This causes:
- Pointer indirection per row access
- Non-contiguous memory layout → cache thrashing on matmul
- Full transpose copy on every matmul call

### Solution

**New type: `TritVectorView`** — a non-owning reference to a span of TritWord64s:
```cpp
class TritVectorView {
    TritWord64* data_;
    size_t size_;       // number of trits
    size_t num_words_;  // number of TritWord64s
public:
    Trit operator[](size_t i) const;
    void set(size_t i, Trit t);   // mutation through view (writes to underlying data)
    int dot(const TritVectorView& other) const;  // delegates to simd::batch_dot
    int hamming(const TritVectorView& other) const;
    int l0_norm() const;
    // Same read/write API as TritVector, but non-owning
};
```

**Lifetime semantics:** `TritVectorView` does not own its data. It must not outlive the `TritVector` or `TritMatrix` it references. This is the same pattern as `std::string_view` or `std::span`. Views are lightweight (pointer + two size_t) and intended for parameter passing, not long-term storage.

**Refactored TritMatrix** — single contiguous buffer:
```cpp
class TritMatrix {
    std::vector<TritWord64> data_;  // flat, contiguous
    size_t rows_, cols_, words_per_row_;

    TritVectorView row(size_t r);  // returns view into data_
};
```

`TritVector` gains implicit conversion to `TritVectorView`. All functions that take `const TritVector&` now take `TritVectorView` instead, making them work with both owned vectors and matrix row views.

### matmul Improvement
With contiguous storage, blocked matmul becomes possible:
- Transpose only the active block (fits L1 cache ~32KB)
- Process 64×64 trit tiles
- ~2-3x improvement for matrices > 128×128

### Files Modified
- New: `trit_view.h` — TritVectorView
- `trit_vector.h` — add conversion to view, move dot/hamming/l0 to accept views
- `trit_matrix.h` — replace vector-of-vectors with flat storage, blocked matmul
- Tests updated for view semantics

## Change 3: Word-Level Convolution

### Problem
`conv1d`/`conv2d`/`conv3d` use `to_int(input[i+k])` per element. Each `operator[]` call computes `i / 32` and `i % 32` (division + modulo). For a 1024-element input with a 32-element kernel, that's 32K modular arithmetic ops.

### Solution
Pre-extract kernel to `int[]` once, then iterate over input words directly:

```cpp
std::vector<int> conv1d(const TritVector& input, const TritVector& kernel) {
    // Pre-extract kernel values once
    std::vector<int> k_vals(kernel.size());
    for (size_t i = 0; i < kernel.size(); ++i)
        k_vals[i] = to_int(kernel[i]);

    // Main loop: extract input trits in word-sized batches
    for (size_t i = 0; i < out_len; ++i) {
        int sum = 0;
        size_t base_word = (i) / 32;
        int base_bit = (i) % 32;
        // Extract directly from word data without per-element operator[]
        // ...
    }
}
```

For small kernels (3-7 elements), unroll the inner loop entirely. For large kernels, use `dot()` on sub-views.

**conv2d approach:** Pre-extract kernel rows to `int[]`. For each output pixel, iterate over kernel rows and compute partial dot products using word-level access on the contiguous matrix data. With contiguous TritMatrix (Change 2), row data is sequential in memory, enabling prefetch-friendly access patterns.

**conv3d:** Same optimization but operates on packed Volume3D (Change 6).

### Files Modified
- `convolution.h` — rewrite conv1d/conv2d/conv3d inner loops
- `convolution.h` — Volume3D uses TritWord64 storage (see Change 6)

### Expected Impact
~3-7x for conv2d on 256×256+ inputs with kernels > 3×3

## Change 4: Aligned Allocator

### Problem
`std::vector<TritWord64>` uses default allocator which doesn't guarantee cache-line alignment. On modern CPUs, unaligned access across cache lines costs ~10-15% additional latency.

### Solution
```cpp
// New: alignment.h
template<typename T, size_t Alignment = 64>
struct AlignedAllocator {
    using value_type = T;
    T* allocate(size_t n);    // uses _aligned_malloc (MSVC) or aligned_alloc
    void deallocate(T* p, size_t n);
};

// Usage in TritVector:
using AlignedWordVec = std::vector<TritWord64, AlignedAllocator<TritWord64>>;
```

Applied to TritVector's internal storage and TritMatrix's flat buffer.

### Files Modified
- New: `alignment.h`
- `trit_vector.h` — use aligned allocator
- `trit_matrix.h` — use aligned allocator

### Expected Impact
~5-15% speedup on SIMD-heavy paths (aligned `_mm256_load_si256` vs unaligned `_mm256_loadu_si256`)

## Change 5: API Polish

### Missing Operators
```cpp
// TritVector additions:
bool operator==(const TritVector& other) const;
TritVector operator+(const TritVector& other) const;  // saturating add
TritVector operator*(const TritVector& other) const;  // element-wise multiply

// Move semantics (defaulted):
TritVector(TritVector&&) = default;
TritVector& operator=(TritVector&&) = default;
TritMatrix(TritMatrix&&) = default;
TritMatrix& operator=(TritMatrix&&) = default;
```

### Wire operator-() to SIMD
Current `TritVector::operator-()` has manual bit-twiddling. Replace with call to `simd::batch_negate()`.

### Files Modified
- `trit_vector.h` — add operators, move semantics, wire to simd
- `trit_matrix.h` — add move semantics

## Change 6: Packed Volume3D

### Problem
`Volume3D` in `convolution.h` stores `std::vector<Trit>` — one byte per trit. For a 64^3 volume, that's 256KB instead of 32KB packed.

### Solution
Replace with TritWord64-backed storage:
```cpp
struct Volume3D {
    std::vector<TritWord64> words_;
    size_t depth, height, width;
    size_t total_trits_;

    Trit get(size_t d, size_t h, size_t w) const {
        size_t idx = d * height * width + h * width + w;
        return words_[idx / 32].get(idx % 32);
    }
    void set(size_t d, size_t h, size_t w, Trit t) {
        size_t idx = d * height * width + h * width + w;
        words_[idx / 32].set(idx % 32, t);
    }
};
```

### Files Modified
- `convolution.h` — rewrite Volume3D internals
- `test_trit_convolution.cpp` — update Volume3D construction

## Change 7: CUDA Kernels

### Architecture
Follow the engine's existing pattern:
- `cuda/tritium_kernels.cu` — device kernels
- `include/tritium/tritium_cuda.h` — host-side launch wrappers + device memory types
- Guarded by `FTD_ENABLE_CUDA` in CMake

### Device Types
```cpp
// Host-side wrapper for device memory
class TritDeviceVector {
    uint64_t* d_words_;  // device pointer to TritWord64 data
    size_t size_;
    size_t num_words_;
public:
    TritDeviceVector(size_t n);                     // allocate on device
    TritDeviceVector(const TritVector& host_vec);   // upload
    void download(TritVector& host_vec) const;      // download
    ~TritDeviceVector();                            // cudaFree
};

class TritDeviceMatrix {
    uint64_t* d_data_;
    size_t rows_, cols_, words_per_row_;
public:
    TritDeviceMatrix(const TritMatrix& host_mat);
    void download_results(std::vector<int>& result) const;
};
```

### Kernels
```cpp
// 1. Batch dot product: N independent dot products in parallel
//    Each thread block handles one vector pair
__global__ void trit_batch_dot_kernel(
    const uint64_t* a_words,    // N vectors concatenated
    const uint64_t* b_words,    // N vectors concatenated
    int* results,               // N results
    int words_per_vec, int n_pairs);

// 2. Matrix-vector multiply: one thread block per row
__global__ void trit_matvec_kernel(
    const uint64_t* matrix_data,
    const uint64_t* vec_data,
    int* results,
    int words_per_row, int n_rows);

// 3. Batch quantize: convert doubles to packed trits on GPU
__global__ void trit_quantize_kernel(
    const double* src, uint64_t* dst_words,
    int n, double threshold);
```

### Thread Configuration
- Dot product: 256 threads/block, warp-level reduction using `__shfl_down_sync`
- Matvec: 1 block per row, shared memory for vector caching
- Quantize: 256 threads/block, coalesced memory access

### CMake Integration

Separate target from `ftd_cuda` — tritium CUDA has no engine dependency.

```cmake
if(FTD_ENABLE_CUDA)
    add_library(tritium_cuda cuda/tritium_kernels.cu)
    target_include_directories(tritium_cuda PUBLIC ${CMAKE_SOURCE_DIR}/include)
    target_link_libraries(tritium_cuda CUDA::cudart)
    set_target_properties(tritium_cuda PROPERTIES
        CUDA_SEPARABLE_COMPILATION ON
        CUDA_RESOLVE_DEVICE_SYMBOLS ON)
    target_compile_options(tritium_cuda PRIVATE
        $<$<COMPILE_LANGUAGE:CUDA>:--expt-relaxed-constexpr --allow-unsupported-compiler>)

    add_executable(test_trit_cuda tests/test_trit_cuda.cpp)
    target_link_libraries(test_trit_cuda tritium_cuda CUDA::cudart)
    add_test(NAME trit_cuda COMMAND test_trit_cuda)
endif()
```

`TritDeviceVector` follows RAII with move semantics: no copy constructor, movable only, destructor calls `cudaFree` with error checking via the engine's existing `CUDA_CHECK` pattern.

### Expected Impact
- Batch dot product: ~100-300x vs CPU for 10K+ vector pairs
- Matvec: ~50-200x for matrices > 1024×1024 (smaller matrices dominated by transfer overhead)
- RTX 5090 target: leverage existing engine CUDA 13.0 setup
